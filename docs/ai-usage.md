# AI 使用说明

> 交付物 3。记录本项目在 AI 辅助下的关键帮助点、未采纳的 AI 建议，以及人为做出的关键决策与理由。关注点是「如何在 AI 辅助下做工程决策」，而非需求本身是否完成。

## 1. AI 的关键帮助点

- **需求拆解与边界梳理**：把 readme 的散述归纳为「接入 / 存储 / 投递 / 观测」四条链路，并逐条追问「哪些属于本系统、哪些属于外部供应商职责」，帮助快速定形系统边界（design.md §3）。
- **可靠性方案脑暴**：投递语义（at-least-once）、状态机（5 态）、指数退避 + full jitter + 上限、可见性超时回收（reap）等模式，由 AI 给出候选并解释权衡，人来裁剪。
- **样板与实现**：workspaces 脚手架、Fastify JSON Schema、better-sqlite3 事务写法、Vite+React 面板组件、vitest 用例，AI 生成初稿后人工审校。
- **测试用例设计**：claim 取件互斥、退避区间边界、状态码分类、reap 回收、端到端黑盒（stub 外部服务）等用例的枚举，AI 帮助覆盖易漏的边界。

## 2. 未采纳的 AI 建议（及原因）

AI 在方案发散阶段给出过若干「更完整」的设计，均因**与 MVP 规模不匹配、属过度设计**而被否决：

| AI 建议 | 未采纳原因 |
|---|---|
| 引入 Kafka / RabbitMQ / Redis 作为消息队列 | 中等量级的内部网关引入独立中间件，部署与运维成本远超收益；SQLite 事务型 outbox 已同时提供持久化、队列与至少一次语义。 |
| 加入熔断器（circuit breaker）| 「长期不可用不放大故障」已由退避上限 + 死信 + 并发上限覆盖。per-host 滑窗/half-open 是为「尚未出现的单目标队头阻塞」提前付费——列为演进触发条件而非第一版内容。 |
| 接入 OpenTelemetry / 分布式追踪 | 单进程单节点场景，结构化日志 + `/stats` + 状态查询已足够排障。 |
| 拆分 `outbox` 与 `notifications` 两张表 | 通知请求本身即待投递项，没有独立领域实体需要分离，单表更简单且够用。 |
| 抽象出可插拔存储层 / Repository 泛型接口 | YAGNI。一个内聚的 `store.ts` 就是未来迁库（Postgres）的天然改动边界，提前泛化只增负担。 |
| 支持鉴权 / 多租户 / 动态限流 | 定位为内部可信网络的基础设施，这些能力应由上游或按演进需要引入，放进第一版会稀释核心。 |
| 捕获并转发外部响应体、Webhook 签名校验 | 需求明确「业务方不关心返回值」，只读状态码判定成败即可。 |

## 3. 人为做出的关键决策（及理由）

- **用 better-sqlite3 的同步事务消灭并发复杂度**：`claimBatch` 在 `BEGIN IMMEDIATE` 事务里完成「选中 → 置 delivering」，同步执行使其天然原子。相比引入锁服务/租约/leader 选举，这是用语言特性把问题消灭，而非用架构去解决一个本不该存在的问题。
- **区分「提交侧幂等」与「投递侧至少一次」**：两者是不同层面的问题——前者用 `Idempotency-Key + UNIQUE` 防重复入库，后者接受重复送达并把去重交给对端。各用最轻的手段，而不是用一个「exactly-once」的大锤同时砸两颗钉子。
- **退避上限 + 死信 取代熔断器**：明确「长期不可用」的兜底目标，选择成本最低、可解释的方案覆盖它。
- **选 better-sqlite3 而非 `node:sqlite`**：后者需 Node 22.5+ 且仍是 experimental，与 readme 约定的 Node 18+ 冲突；前者稳定、自带预编译二进制、安装门槛低。
- **前端克制在「可观测面板」**：只做提交 + 列表/详情/手动重试，用轮询而非 WebSocket/SSE。前端偏重对一个 webhook 网关是过度设计，与评分「警惕过度设计」一致。
- **单仓多包 + common 契约**：前后端共享同一份类型与「可重试状态码」定义，避免两端产生分歧，是全栈 TS 的收益点。

## 4. 复杂度管理的一句话总结

把复杂度**只花在已被需求证明的问题上**；对尚未出现的问题，用 `design.md §5` 的演进路线记录「触发条件」，而不是提前实现。这是本项目所有取舍的统一判断依据。
