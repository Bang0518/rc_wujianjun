# 接入指南（业务方）

> 面向**接入本服务的业务开发**。你只需把「要通知谁、发什么」提交给网关，**重试、失败兜底、可观测由网关负责，你无需自己实现重试逻辑**。
> 完整字段参考见 [`api.md`](api.md)；本文档重点是「如何正确接入 + 避免踩坑」。

## 1. 何时用它

关键业务事件发生时需要调用**外部供应商 HTTP API** 发通知，且你**只关心可靠送达、不关心对方返回值**。典型场景：

- 用户注册成功 → 通知广告系统
- 订阅付款成功 → 通知 CRM 改状态
- 下单成功 → 通知库存系统

## 2. 快速开始

```bash
curl -X POST http://<网关地址>/notifications \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://vendor.example.com/webhook",
    "method": "POST",
    "headers": { "Authorization": "Bearer <你的对外token>" },
    "body": { "event": "user_registered", "user_id": "123" }
  }'
```

返回字段如下：

```json
{ "id": "9762f4ce-...", "status": "pending", "createdAt": 1710000000000 }
```

记下 `id`，后续可用它查询投递状态。

## 3. 提交字段说明

`POST /notifications`，`Content-Type: application/json`。

| 字段 | 类型 | 必填 | 你该怎么填 |
|---|---|---|---|
| `url` | string | 是 | 目标地址，必须 `http://` 或 `https://` 开头 |
| `method` | string | 否 | `GET/POST/PUT/PATCH/DELETE`，默认 `POST` |
| `headers` | object | 否 | 转发给目标的请求头，**鉴权 token 放这里** |
| `body` | any | 否 | 任意 JSON；对象会被序列化，字符串原样发送；`GET` 不带 |
| `maxAttempts` | integer | 否 | 覆盖默认最大尝试次数（1–100，默认 8） |

可选请求头：`Idempotency-Key: <你的业务唯一串>`（见下一节）。

## 4. 专有名词理解

**① 异步：`202` ≠ 已送达。**
返回 `202` 只代表「网关收到并已持久化」。真正投递是后台异步进行的。
要确认是否送达，必须查状态（见 §5），**返回 202 不代表投递成功**。

**② 目标可能收到重复投递。**
网关保证 尽力送达、失败重试，因此在极端情况（如投递成功但记录状态前网关崩溃）下，**同一条通知可能被投递多次**。建议在 `body` 里带一个业务唯一 ID，以便目标系统自行去重。

**③ 提交去重用 `Idempotency-Key`。**
如果**业务侧**因网络抖动重试了 POST，带上同一个 `Idempotency-Key`，网关会返回**已存在的那条记录**（`200`，不新建）。key 建议用你的业务主键，如 `order-9001`。注意：这解决的是「你重复提交」，与 ② 的「目标重复收到」是两回事。

**④ 网关不回传目标的响应体。**
成败只由**目标返回的状态码**判定，网关不会把对方响应内容返回给你。如果你需要对方的返回数据，本网关不适用。

## 5. 查询投递状态

```bash
curl http://<网关地址>/notifications/<id>
```

返回完整记录，重点看 `status` 与 `attempts` / `lastError` / `lastStatusCode`：

| status | 含义 | 你该做什么 |
|---|---|---|
| `pending` | 待投递 / 重试等待中 | 等待，稍后再查 |
| `delivering` | 投递中 | 等待 |
| `succeeded` | 已送达（2xx） | 完成 ✅ |
| `failed` | 永久失败（如 400/401/404） | 请求本身有问题，改正后重新提交 |
| `dead_letter` | 反复失败进死信（目标长期不可用） | 排查目标，或手动重试（§6） |

> 也可打开网关自带的**可观测面板**（浏览器访问网关地址）直接查看，无需写查询代码。

## 6. 重试策略与失败处理

网关如何对待目标的响应：

| 目标响应 | 网关处理 |
|---|---|
| `2xx` | 成功 → `succeeded` |
| `408` / `429` / `5xx` | 可重试：指数退避后重试，耗尽次数 → `dead_letter` |
| 网络错误 / 超时 | 同上（可重试） |
| 其他 `4xx`（400/401/404…） | 永久失败 → `failed`，**不重试** |

重试节奏为**指数退避 + 抖动**：约 1s、2s、4s、8s……最长间隔封顶 1 小时，默认最多 8 次（可用 `maxAttempts` 覆盖）。这样既不放弃，也不会把已故障的目标打垮。

**手动重放**：对 `failed` / `dead_letter` 的记录，可重置为 `pending` 再投一次（`attempts` 归零）：

```bash
curl -X POST http://<网关地址>/notifications/<id>/retry
```

## 7. 常见约定

- `url` 必须以 `http(s)://` 开头；出于安全，网关**不跟随重定向**。
- 鉴权 token 等放在 `headers` 里由网关**原样转发**；网关不为你管理凭证。
- `body` 传对象会被序列化为 JSON；传字符串原样发送。
- 单次投递超时默认 10s；请确保目标能在此时间内响应。
- 网关面向内部可信网络，**不做调用方鉴权/限流**——请勿把它直接暴露到公网。
